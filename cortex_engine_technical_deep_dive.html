High-Resolution Technical Architecture Whitepaper

Technical Deep Dive of PolicyRank-RL: CORTEX Engine

A contract-native, agentic, reinforcement-learning architecture for e-commerce product search. CORTEX transforms queries into executable search contracts, evaluates competing contract strategies, mutates policy rules through RL, compiles them into ranking functions, and constructs diversified product-result slates through cooperative rank-position agents.

CORTEX = Contract-Oriented Reinforcement for Task-Executable Search

1. Technical thesis

CORTEX is a meta-ranking engine. A classic ranker learns a direct product score. CORTEX learns the higher-level control policy that decides which ranking contract should be executed, how it should be repaired, how it should be mutated, and how the final product slate should be assembled.

Key technical claim: The central learnable object is not only the product ranking. The central learnable object is the contract-to-policy transformation: how natural-language intent becomes constrained, auditable, executable ranking behavior.
Input

Query

A short, ambiguous shopping intent such as “cheap headphones” or “quiet bathroom fan”.

Plan

Contract

Structured objectives, constraints, guardrails, reward definitions, and ranking weights.

Learn

RL Control

Q-learning and mutation policies learn which contract operations improve slates.

Output

Slate

A ranked page of products with explanations, diversity, and reward traceability.

2. Why existing systems do not fully solve this

Modern product search systems are powerful but usually optimize relevance, personalization, or conversion through opaque ranking models. CORTEX adds a new abstraction layer: executable search contracts. This creates a controllable bridge between intent, business rules, compliance, ranking weights, and reinforcement learning.

5. Search contract: the technical control object

A contract is a normalized, executable representation of user intent and ranking behavior. It can be logged, compared, validated, versioned, mutated, and compiled. That makes it more powerful than a prompt, query embedding, or ranking feature vector.

Why it matters for ML

The contract becomes a state-bearing feature object. It lets the RL layer condition policy decisions on intent, not just product features.

Why it matters for product

Product teams can inspect or edit objectives and guardrails without directly editing model code.

Why it matters for trust

Every slate can be explained by the contract that produced it, the mutation applied, and the policy weights used.

6. Contract Arena: multi-agent contract generation

The Contract Arena creates several candidate contracts per query. Instead of trusting one planner, CORTEX asks specialized agents to propose competing hypotheses about what the user really wants.

Contract agentOptimization biasFailure it preventsExample output
Relevance AgentExact product match and semantic/lexical alignment.Prevents over-personalized or cheap but irrelevant results.Boost ESCI Exact and semantic score.
Price AgentAffordability after relevance threshold.Prevents expensive items dominating budget queries.Add price score but require relevance floor.
Quality AgentRatings, premium signals, strong match confidence.Prevents low-quality cheap products from ranking high.Boost rating and exactness for “best” queries.
Diversity AgentSubtopic and product-type spread.Prevents top results from becoming near-duplicates.Require diversity@5 above a threshold.
Exploration AgentSubstitutes, complements, low-confidence discovery.Prevents search from getting stuck in known high-frequency products.Allocate one controlled exploration slot.
Guardrail CriticSafety and contract validity.Prevents invalid ranking instructions and irrelevant top results.Reject contract if Irrelevant@3 > 0 when exact candidates exist.
Technical nuance: This is not “multiple prompts for fun.” It creates a structured action set for RL. Each agent’s contract becomes a candidate policy that can be counterfactually evaluated and learned from.

7. RL architecture: from slate Q-learning to contract mutation

7.1 MDP formulation

ComponentCORTEX definitionWhy it matters
State sEncoded search contract + query context + retrieval confidence + slate diagnostics + user persona.Lets the system learn different behavior for different query intents.
Action aSelect contract, mutate contract, repair contract, blend contracts, choose compiler strategy, or allocate exploration.Makes RL operate at the policy-control level, not only item-ranking level.
Reward rComposite slate reward using ESCI, clicks, diversity, contract satisfaction, and regret penalty.Optimizes the whole search page instead of a single item.
Policy πMapping from contract state to a contract operation.Defines how CORTEX chooses the best search strategy over time.
TransitionOne-step in current MVP; session-level later with query refinements and user feedback loops.Allows future extension to long-horizon search sessions.

7.2 Core Q-learning

Q(s,a) ← Q(s,a) + α [ r + γ maxa′Q(s′,a′) − Q(s,a) ]

In the current MVP, Q-values are tabular and stored per contract state/action. This keeps the system explainable. In the full version, the Q-function can become a learned approximator using state embeddings and contract features.

7.3 Contract mutation RL

The most advanced version of CORTEX treats contract edits as RL actions. The model learns which edit improves a slate under which search context.

C′ = M(C, amutation)
rmutation = Reward(Slate(C′)) − Reward(Slate(C))
Mutation action examples: - increase_esci_weight(+0.10) - add_no_irrelevant_top3_guardrail() - increase_diversity_floor(0.60 → 0.72) - allocate_one_substitute_slot() - reduce_price_weight_if_relevance_low() - blend(price_agent, relevance_agent, ratio=0.35/0.65)

7.4 Counterfactual tournament and regret

Because ESCI labels exist offline, CORTEX can evaluate many contracts on the same query without needing to expose each version to a real user. This creates an offline policy improvement loop.

C* = argmaxCᵢ∈Arena Reward(Slate(Cᵢ))
Regret(Cchosen) = Reward(C*) − Reward(Cchosen)

Regret is important because a high reward alone does not show whether the selected policy was optimal. If the chosen contract gets 0.71 reward but another counterfactual contract gets 0.88, the system knows it left 0.17 reward on the table.

8. Policy compiler: where contracts become executable ranking

The compiler is the boundary between symbolic/agentic planning and numeric ranking. It converts a validated contract into a scoring function that can rank actual products.

Score(p|q,C,a)=wlexL(p)+wsemS(p)+wesciE(p)+wpriceP(p)+wratingR(p)+wdivD(p)+wexpX(p)
FeatureSourceCompiler role
L(p)TF-IDF/BM25Ensures exact terms and product-type terms matter.
S(p)Sentence Transformer / FAISSCaptures semantic match beyond exact words.
E(p)ESCI label or relevance predictorGrounds reward in product-search relevance.
P(p)Price/affordabilitySupports budget-sensitive queries.
R(p)Rating/quality proxySupports quality-sensitive queries.
D(p)Title/embedding diversityPrevents repetitive result pages.
X(p)Novelty/cold-start proxySupports controlled discovery.
Why this is important: The compiler lets the system remain auditable. A product did not rank high because “the model said so”; it ranked high because a contract selected a policy and that policy assigned explicit weights to interpretable signals.

9. Multi-agent slate workers

The final page is built by rank-position agents. Each worker observes the remaining candidates and already selected slate prefix. It chooses one product for its rank position.

AgentScore(p,i)=λrel,iRel(p)+λpolicyPolicyScore(p)+λdiv,iDiversity(p,S<i)+λguardGuardrailScore(p)
Diversity(p,S<i) = 1 − maxs∈S<iSimilarity(p,s)
Slate Prefix
Rank 1 WorkerSelects highest contract-satisfying exact result.
Rank 2 WorkerSelects high-relevance but avoids near-duplicate.
Rank 3 WorkerAdds comparison option or substitute if contract permits.
Rank 4 WorkerBalances quality and diversity.
Rank 5 WorkerCompletes slate under guardrails and reward objective.

This is technically different from a simple sort. A simple sort assumes independent item scores. The multi-agent layer makes the slate context-aware: each selected item changes the value of the remaining items.

10. Reward architecture and evaluation metrics

CORTEX uses reward decomposition because a single metric is too fragile. Clicks alone can reward clickbait; relevance alone can ignore diversity; diversity alone can hurt exactness. The final reward should be balanced.

ItemReward(p)=0.70·ESCI(p)+0.30·ClickReward(p)
SlateReward@K=\frac{Σ_{i=1}^{K} position_weight(i)·ItemReward(p_i)}{Σ_{i=1}^{K} position_weight(i)}
FinalReward=β₁·SlateReward + β₂·NDCG@K + β₃·Diversity@K + β₄·ContractSatisfaction − β₅·IrrelevantPenalty − β₆·Regret
MetricMeaningWhy it matters
Precision@KRelevant items in top K.Measures top-page relevance.
NDCG@KDiscounted gain by rank.Rewards relevant items near the top.
SlateReward@KPosition-weighted reward for the whole slate.Primary RL feedback signal.
Diversity@KAverage dissimilarity across top-K products.Prevents repetitive search pages.
Irrelevant@KCount of irrelevant items in top-K.Guardrail and quality diagnostic.
Regret@KBest counterfactual reward minus chosen reward.Shows how far the system is from optimal policy choice.
Contract SatisfactionWeighted compliance with contract rules.Ensures the ranker follows the user intent and constraints.

18. Final technical positioning

CORTEX should be framed as a contract-native RL control plane for e-commerce search. It is not trying to replace every search engine immediately. It can sit above existing retrieval/ranking infrastructure and provide the missing layer: auditable intent contracts, RL-based contract optimization, multi-agent slate construction, and reward/regret analytics.

Final one-liner: PolicyRank-RL: CORTEX Engine learns how to transform user intent into executable ranking contracts, optimize those contracts through reinforcement learning, and assemble better e-commerce search pages through cooperative multi-agent slate workers.
