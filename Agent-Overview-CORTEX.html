Agent Overview - Deep Technical Dive: CORTEX Engine

CORTEX is a multi-agent, contract-aware, reinforcement-learning-inspired search reranking engine. It converts a raw shopping query into a structured intent contract, applies policy-aware filtering and slate optimization, diversifies the result set, and uses a baseline-aware safety gate to decide when to trust, lightly rerank, or fully override the semantic baseline.

1. Executive summary

Standard product search systems typically retrieve a candidate set, compute relevance scores, and sort products with either lexical, neural, or learning-to-rank models. CORTEX extends this paradigm with an explicit agentic control layer: agents inspect the query, infer user intent, create a machine-readable search contract, enforce constraints, select a ranking policy, diversify the slate, and then determine whether CORTEX should fully rerank or defer to a strong baseline.

What makes it agentic?

CORTEX is not a single scoring function. It is a coordinated decision system with specialized modules that observe state, execute ranking actions, produce intermediate artifacts, and feed logs into future policy updates.

What does it optimize?

The current offline objective is SlateReward@5, combining simulated user feedback with relevance-oriented slate quality. The system compares semantic baseline, full CORTEX, and gated CORTEX.

Why is it better?

It attacks common failure modes in product search: semantic false positives, query-intent mismatch, over-reranking, under-diversified slates, and brittle dependence on a single model score.

2. CORTEX system architecture

The system is best understood as an orchestration graph. Each agent receives a state representation, produces either a transformed candidate set or a control decision, and passes structured information to the next stage.

3. Agent-by-agent deep technical dive

Each CORTEX agent is a specialized decision component. The power comes from composing them: the output of one agent becomes the structured state used by the next.

01

Semantic Retrieval Agent

The retrieval agent uses cached dense embeddings to convert lexical query text into vector-space candidate retrieval. It produces the initial top-K candidate pool that downstream CORTEX agents operate on.

Input

q = user query
D = product catalog rows
E(q), E(d_i) = embedding vectors

Operation

score(q, d_i) = cosine(E(q), E(d_i))
C_K = topK_d score(q, d)

Why it improves standard search

  • Captures semantic similarity beyond exact token overlap.
  • Supports multilingual/noisy product queries better than pure lexical scoring.
  • Creates a strong baseline that the gate can preserve when already reliable.
02

LLM Contract Agent

The LLM Contract Agent transforms an ambiguous shopping query into a structured machine-readable search contract. This is the intent layer that standard ranking pipelines usually lack.

Output schema

{
  "intent": {
    "detected_category": "...",
    "product_type": "...",
    "price_sensitivity": "...",
    "quality_preference": "...",
    "ambiguity_level": "..."
  },
  "dynamic_filters": {
    "must_have_terms": [...],
    "blocked_terms": [...]
  }
}

Technical function

  • Converts unstructured query language into explicit constraints.
  • Separates hard requirements from soft preferences.
  • Creates an auditable intermediate artifact for downstream enforcement.
03

Contract Filter Agent

This agent applies the search contract to candidate products before expensive reranking logic. It reduces semantic false positives and filters candidates that violate inferred user intent.

Decision score

match_score(d) =
  w_required * required_term_match(d)
+ w_preferred * preferred_term_match(d)
- w_blocked  * blocked_term_violation(d)

Why it matters

  • Semantic similarity can retrieve plausible but intent-misaligned products.
  • Filtering early reduces downstream ranking noise.
  • It makes the ranking pipeline constraint-aware, not just score-aware.
04

Slate Q-Learning Policy Agent

The Slate Q-Learning Agent chooses a ranking action based on the current contract state and retrieval confidence. It represents the RL side of CORTEX: the system is not only scoring products but selecting ranking policies.

State abstraction

s_t = {
  retrieval_confidence,
  contract_strength,
  ambiguity_level,
  coverage_status
}

Action abstraction

a_t ∈ {
  semantic_priority,
  contract_priority,
  diversity_priority,
  brand_priority,
  exploration_priority
}

Reward

R(slate@5) = SlateReward@5

Slate-oriented RL is motivated by the fact that user response depends on the whole slate, not simply an independent item score.

05

Policy Compiler Agent

The policy compiler translates the selected RL action into concrete ranking weights. This creates a bridge between high-level policy selection and low-level scoring.

Example

final_score(d) =
  α * semantic_score(d)
+ β * contract_match(d)
+ γ * brand_preference(d)
+ δ * diversity_utility(d)

Technical advantage

  • Allows the system to change ranking behavior dynamically per query.
  • Keeps policy choices interpretable.
  • Supports experimentation over ranking action spaces.
06

Final Slate Enforcement Agent

This agent performs a post-ranking contract audit. It verifies that the slate still satisfies the search contract after policy scoring.

Enforcement checks

  • Are required terms represented?
  • Are blocked terms leaking into the slate?
  • Does the preferred brand or product type appear when relevant?
  • Is contract coverage too low?

Unlike standard ranking systems that only optimize score order, this layer enforces semantic correctness at the slate level.

07

Multi-Agent Diversifier

The diversifier behaves like a committee of slate specialists. It balances relevance, brand preference, contract priority, and novelty to reduce redundancy in the final page.

Slate objective

U(S) =
  Σ relevance(d_i)
+ λ₁ contract_coverage(S)
+ λ₂ diversity(S)
+ λ₃ brand_alignment(S)
- λ₄ redundancy(S)

Why it matters

  • A top-5 page should not be five near-duplicate products.
  • Diversity improves coverage of ambiguous intent.
  • Slate-level composition is closer to real search UX than item-level sorting.
08

Baseline-Aware Gate Agent

This is the safety controller added in MVP 13.3.1. It decides whether the semantic baseline should be preserved, lightly reranked, or fully overridden by CORTEX.

Gate signals

g = {
  baseline_confidence_score,
  contract_alignment_score,
  top1_score,
  top5_mean_score,
  label_quality_score,
  exclusion_violation_rate
}

Decision

π_gate(g) ∈ {
  preserve_baseline,
  light_rerank,
  full_cortex
}

Why it is important

  • Prevents over-reranking when semantic baseline is already strong.
  • Defaults to full CORTEX when baseline confidence is insufficient.
  • Improved full CORTEX from 167 wins to 175 wins on 250 queries.
09

Feedback + Experiment Memory Agent

This layer logs simulated clicks, rewards, contracts, gate decisions, and evaluation snapshots. It turns CORTEX from a static pipeline into a learning system.

Logged artifacts

  • Per-query baseline reward
  • Per-query gated CORTEX reward
  • Full CORTEX reward
  • Gate decision and reason
  • Contract source and fallback status
  • Lift, win/loss/tie, rescued baseline-loss cases
10

Resilient Contract Fallback Agent

Added to improve scalable evaluation robustness. If LLM contract generation fails, the system generates a local query-term fallback contract rather than failing the entire query.

Fallback logic

if LLM_contract(q) succeeds:
    use LLM contract
else:
    build local fallback contract from query tokens

Why it matters

  • Prevents long evaluations from collapsing due to transient client/API failures.
  • Preserves downstream compatibility with contract filters and gate logging.
  • Supports graceful degradation, a necessary property for production-grade agent systems.

4. Standard ranking stack vs CORTEX agentic ranking

The standard industrial search stack is powerful but typically score-centric: retrieve candidates, compute features, run a ranking model, then sort. CORTEX keeps the strong parts of that pipeline but adds structured intent, slate-level policy control, multi-agent diversification, and a gate that explicitly manages reranking risk.

Conventional ranking pipeline

  • Often optimized for item-level relevance.
  • Weak explicit representation of query intent constraints.
  • Can over-rerank strong baseline results.
  • Hard to audit why a product appeared.
  • Limited slate-level control unless explicitly added.

CORTEX agentic ranking pipeline

  • Combines neural retrieval with explicit intent contracts.
  • Uses policy selection rather than one static scoring recipe.
  • Optimizes slate behavior, not only individual item scores.
  • Routes between baseline, light rerank, and full CORTEX.
  • Logs traces that can train future learned gate/classifier agents.

Why this is technically better than the standard approach

Failure mode in standard ranking CORTEX mechanism Technical effect
Semantic retrieval retrieves plausible but wrong products. LLM Contract Agent + Contract Filter Agent. Introduces explicit intent constraints and blocked-term filtering.
Ranking model treats each item independently. Slate Q-Agent + Multi-Agent Diversifier. Optimizes the whole top-K composition and reduces redundancy.
Strong baseline gets damaged by unnecessary reranking. Baseline-Aware Gate Agent. Routes between preserve, light rerank, and full CORTEX based on confidence/alignment signals.
Pipeline failures stop long evaluations. Resilient Contract Fallback Agent. Maintains evaluation continuity when the LLM contract generator fails.
Black-box ranking decisions are hard to debug. Experiment Memory + Analyzer. Produces per-query traces, reward deltas, gate reasons, and threshold diagnostics.

6. Technical framing

CORTEX can be formalized as a modular policy over a candidate slate. Let the user query be q, the candidate universe be D, the retrieved candidate set be C_K, the LLM contract be κ, and the final slate be S@5.

Formal pipeline

C_K = Retrieve(q, D)

κ = ContractAgent(q, C_K)

C'_K = ContractFilter(C_K, κ)

a = QPolicyAgent(state(q, κ, C'_K))

R = PolicyCompiler(C'_K, a)

S_full = Diversify(Enforce(R, κ))

S_final = Gate(S_baseline, S_full, κ)

Gate objective

Gate should maximize:

E[Reward(S_final) - Reward(S_baseline)]

while minimizing:

P(over_rerank | baseline strong)

and preserving:

contract_alignment(S_final, κ)

Why this is not just reranking

A conventional reranker is usually a mapping from features to a scalar score: f(q, d) → score. CORTEX is closer to a hierarchical policy: π(q, C_K, κ) → {action, slate, trace}. The trace matters because it exposes the internal decisions: contract generation, filter behavior, RL action, enforcement status, gate decision, and reward deltas.

Research-grade novelty angle

  • Contract-aware ranking: Query understanding becomes an enforceable object, not a hidden latent vector.
  • Slate-aware decisioning: The system optimizes top-K page quality rather than individual item relevance only.
  • Risk-aware reranking: The gate explicitly models the risk that reranking harms a strong semantic baseline.
  • Agentic orchestration: Specialized agents coordinate through structured intermediate states.
  • Learning-ready traces: Evaluation logs can train future query difficulty, gate classifier, and reward critic agents.

7. What comes next

The best next step is not another hand-tuned threshold expansion. The failed MVP 13.4 v1 experiment showed that naive expansion can hurt. The next phase should turn the gate into a learned routing policy.

MVP 13.4

Learned Gate Classifier Agent

Train a classifier using evaluator logs to predict which route is best: full CORTEX, light rerank, or baseline preservation. Features include baseline confidence, contract alignment, top-1 score, top-5 mean score, label quality, ambiguity, enforcement status, and historical reward deltas.

MVP 13.5

Query Difficulty Agent

Estimate whether a query is easy, ambiguous, sparse, multilingual, typo-heavy, brand-driven, or attribute-heavy. Query difficulty becomes a first-class state variable for the RL policy and gate.

MVP 13.6

Reward Critic Agent

Add a final critic that inspects the slate for intent mismatch, redundancy, missing constraints, and contract violations before the final result is accepted.

MVP 14

Bandit / RL Feedback Loop

Move from offline simulated reward to a bandit-style policy update loop. Use logged reward outcomes to update route selection and ranking policy over time.

Research

Counterfactual Evaluation + IPS/DR Scoring

Introduce counterfactual estimators for offline evaluation under exposure bias. This makes the project more defensible for publication-oriented ranking/recommender systems work.
